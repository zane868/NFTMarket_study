## 0. 一句话心智模型

先记住三条不变量，后面所有代码都是在实现它们：

1. **订单是唯一记账单位。** 挂卖单时 NFT 进 Vault，挂买单时 ETH 进 Vault，两者都用 `OrderKey` 作为 key。Vault 是"按订单托管"，不是"按用户托管"。
2. **只有 OrderBook 能动 Vault。** `onlyEasySwapOrderBook` 修饰器是资产安全的唯一闸门。
3. **链上是真相，数据库是投影。** `EasySwapSync` 是唯一的写者，Backend 几乎纯读。用户看到的"在售/已成交/已过期"全部是链上事件的派生结果。

判断你对项目的理解是否到位，可以用一个标准：**任何一个功能，你都能说出"此刻资产在哪、哪张表记录了什么、谁负责让两者一致"。**

## 1. 项目解决什么问题

一个 **链上订单簿（on-chain order book）型 NFT 交易市场**。

和常见实现对比：

| 模式 | 代表 | 订单在哪 | 撮合在哪 | 本项目 |
|---|---|---|---|---|
| 链下订单簿 + 链上结算 | OpenSea（早期） | 中心化服务器 | 链下撮合，链上只做转移 | ✗ |
| 链上订单簿 | **本项目** | 合约存储 + 红黑树 | 链上原子撮合 | ✓ |
| AMM / 池子 | Sudoswap | 流动性池 | 曲线定价 | ✗ |

**选择链上订单簿换来了什么**：订单不可篡改、撮合原子、不需要信任中心化服务器、任何人可以构建自己的前端。
**代价**：每笔挂单都要付 Gas、订单簿操作（尤其删除中间节点）成本高、需要索引服务把链上状态投影成可查询数据。

面试/讲解时的定位一句话：

> 这是一个链上订单簿型 NFT 市场。用户挂单/出价后资产进入托管金库，撮合由合约原子完成；链下有一套索引服务把合约事件投影成 MySQL 的可查询数据，再通过只读 API 提供服务。

## 3. 模块职责

### 3.1 合约层（`EasySwapContract/contracts/`）

| 合约 | 职责 | 关键点 |
|---|---|---|
| `EasySwapOrderBook.sol`（1035 行） | 对外的唯一入口：建单、撤单、改单、撮合、批量、提协议费、暂停 | 继承 OrderStorage / ProtocolManager / OrderValidator |
| `EasySwapVault.sol`（167 行） | 托管资产，只允许 OrderBook 调用 | 两个 mapping，key 都是 `OrderKey` |
| `OrderStorage.sol`（342 行） | 订单簿数据结构 | 每个(合集,方向)一棵价格红黑树 + 每个价格档一个 FIFO 链表 |
| `OrderValidator.sol`（107 行） | 订单合法性 + 成交量状态 | `filledAmount[key]`；`CANCELLED = uint256.max` 是哨兵值 |
| `ProtocolManager.sol`（59 行） | 协议费率维护 | 上限 `MAX_PROTOCOL_SHARE = 1000`（即 10%），分母 `TOTAL_SHARE = 10000` |
| `LibOrder.sol`（108 行） | 订单结构 + 哈希 | `OrderKey = keccak(ORDER_TYPEHASH, side, saleKind, maker, hash(nft), price, expiry, salt)` |
| `RedBlackTreeLibrary.sol`（368 行） | 价格档的插入/删除/前驱后继 | 支撑 `getBestPrice` / `getNextBestPrice` |

**继承关系**（理解"一个合约为什么能调这么多函数"的关键）：

```
EasySwapOrderBook
 ├ Initializable / ContextUpgradeable / OwnableUpgradeable
 ├ ReentrancyGuardUpgradeable / PausableUpgradeable
 ├ OrderStorage          → 订单池 + 价格树
 ├ ProtocolManager       → protocolShare
 └ OrderValidator        → filledAmount + EIP712 域名
```

### 3.2 同步层（`EasySwapSync/`）

| 组件 | 职责 |
|---|---|
| `cmd/daemon.go` | 读配置、起服务、pprof、优雅退出 |
| `service/service.go` | 组装 DB / Redis / chainClient / filter / orderManager |
| `orderbookindexer.Service` | **核心**：扫块 → 按 topic 分发 → 写派生表 → 推进断点 |
| `OrderManager`（在 `EasySwapBase`） | 4 个旁路 goroutine：过期时间轮、地板价、挂单数、新挂单队列 |
| `collectionfilter` | 内存白名单：只有已导入的合集才处理事件 |

**事件入口只有 4 个 topic**（`service.go:42-48`）：

```
LogMakeTopic          → handleMakeEvent
LogCancelTopic        → handleCancelEvent
LogMatchTopic         → handleMatchEvent
ERC721ApprovalTopic   → handleApprovalEvent
```

`LogSkipOrder` **故意不处理**——因为跳过意味着链上什么都没发生，DB 也就不该变。这是个值得在讲解时点出来的设计。

### 3.3 后端层（`EasySwapBackend/src/`）

|---|---|---|

## 4. 四条业务链路（含资金流转）

### 链路 A：挂卖单（List）

```
用户
 └ approve(Vault, tokenId)                    ← ERC-721 授权
 └ OrderBook.makeOrders([order])
      └ _makeOrderTry
           ├ 校验：maker == msg.sender / price≠0 / salt≠0 / 未过期 / filledAmount==0
           ├ amount 必须 == 1
           ├ Vault.depositNFT(orderKey, maker, collection, tokenId)   ← NFT 进金库
           ├ _addOrder → 价格树插档 + 同价队列尾部追加
           └ emit LogMake
```

**资产状态**：NFT 在 Vault，Vault 的 `NFTBalance[orderKey] = tokenId`。

### 链路 B：挂买单（Bid）

```
用户
 └ OrderBook.makeOrders([order]) {value: price × amount}
      └ _makeOrderTry
           ├ amount 必须 > 0
           ├ Vault.depositETH(orderKey, amount) {value: ...}          ← ETH 进金库
           ├ _addOrder
           └ emit LogMake
      └ 多付的 ETH 退回
```

**资产状态**：ETH 在 Vault，`ETHBalance[orderKey] = 总价`。注意记账是**总价**，不是单价。

区分两种 Bid：

| 类型 | saleKind | 匹配范围 |
|---|---|---|
| Item Bid | `FixedPriceForItem` | 只能匹配指定 tokenId |
| Collection Bid | `FixedPriceForCollection` | 合集内任意 tokenId |

### 链路 C：成交（两条分支，必须讲清区别）

**分支 1：卖家接受 Bid**（`_matchOrder` 第 1 个分支，`EasySwapOrderBook.sol:775` 起）

```
触发者：sellOrder.maker
要求：msg.value 必须 == 0
成交价：buyOrder.price
流程：
  1. Vault.withdrawETH(buyOrderKey, fillPrice, OrderBook)   ← 币从金库到合约
  2. 卖家 += fillPrice - protocolFee
  3. 协议费留在 OrderBook 合约里
  4. NFT：若卖单在簿 → Vault.withdrawNFT 给买家
          否则（临时卖单）→ Vault.transferERC721 直接从卖家转给买家
```

**分支 2：买家买挂单**（第 2 个分支）

```
触发者：buyOrder.maker
成交价：sellOrder.price        ← 注意：取卖单价，不是买单价
流程：
  1. 若买单已在簿：Vault.withdrawETH 取出 buyPrice
     若买单是临时的：要求 msg.value >= fillPrice
  2. 卖家 += fillPrice - protocolFee
  3. 买家多付的部分（buyPrice - fillPrice）退回
  4. Vault.withdrawNFT 给买家
  5. 返回 costValue（批量撮合用来累计花费）
```

**为什么买家不需要先挂 Bid**：前端直接构造一个临时 Bid（不入簿），和卖单一起提交 `multicall`，由合约临时撮合。这是理解"即时购买"的关键。

**协议费去哪了**：留在 OrderBook 合约余额里，`onlyOwner` 通过 `withdrawETH(recipient, amount)` 提取（`EasySwapOrderBook.sol:1000`）。**不是**自动转给某个收款地址。

### 链路 D：撤回与改价

**撤单**（`_cancelOrderTry:597`）：

```
条件：order.maker == msg.sender 且 filledAmount < amount
List → Vault.withdrawNFT 退回卖家
Bid  → Vault.withdrawETH(单价 × 未成交数量) 退回买家
→ _cancelOrder 把 filledAmount 置为 CANCELLED 哨兵
→ emit LogCancel
```

**改价**（`_editOrderTry:665`）本质是"撤旧 + 建新"：

```
1. 校验：saleKind / side / maker / collection / tokenId 都不能变，只能改 price 和 amount
2. _removeOrder(旧) + _cancelOrder(旧) + emit LogCancel
3. _addOrder(新) + emit LogMake
4. List → Vault.editNFT 把 NFT 记账迁到新 key
   Bid  → Vault.editETH 多退少补
```

**这个设计的重要后果**：改价在链上产生**两条事件**，所以数据库里会看到"旧单 Cancelled + 新单 Active"两行。讲数据流时必须说清楚。

### 链路 E：过期（**链上什么都没发生**）

```
OrderManager 时间轮（3600 槽，1 秒 1 格）
  ├ 启动时把所有 Active 订单按 expire_time 装进轮子
  ├ 到点 → UPDATE order_status = Expired
  └ 推一个 Expired 事件 → 触发地板价重算
```

**关键结论**：过期只是数据库标记。`filledAmount` 没变、Vault 里的资产没动、合约上没有任何交易。用户必须自己发 `cancelOrders` 才能取回 NFT/ETH。因为撤单只检查 `filledAmount < amount`，**不检查是否过期**，所以过期后仍可撤单。

这正是最近那个 commit `0bdbf29` 要解决的问题：前端以前用 `list_order_id` 判断能不能撤单，过期订单这个字段是空的，按钮被禁用，NFT 就永远锁在 Vault 里了。修复方式是改为读链上 `Vault.NFTBalance(orderKey)`——**又一次"链上是真相"的体现**。

## 5. 数据流转与一致性

### 5.1 表与写者

| 表 | 写者 | 写入时机 | 幂等键 |
|---|---|---|---|
| `ob_order_<chain>` | Sync | LogMake 插入；Match/Cancel 更新；过期定时改状态 | `order_id` |
| `ob_item_<chain>` | Sync + Backend | 挂单改 list_price；成交改 owner | `(collection_address, token_id)` |
| `ob_item_external_<chain>` | Sync | 挂单后拉 tokenURI | `(collection_address, token_id)` |
| `ob_activity_<chain>` | Sync | 四类事件都写 | `(tx_hash, collection_address, token_id, activity_type)` |
| `ob_collection_<chain>` | Sync | 地板价、数量统计 | `address` |
| `ob_collection_floor_price_<chain>` | Sync 定时 | 每 10 秒全量快照 | `(collection_address, price, event_time)` |
| `ob_indexed_status` | Sync | 每批结束 | `(chain_id, index_type)` |
| `ob_user` | Backend | 登录 | `address` |

**幂等的实现方式**：唯一键 + `clause.OnConflict{DoNothing: true}`。所以同步服务天然可以重复消费同一个事件。

### 5.2 扫块主循环（`service.go:117`）

```
读断点 lastSyncBlock
loop:
  currentBlock = RPC
  safeEndBlock = currentBlock - 确认块数(8)
  若 lastSyncBlock > safeEndBlock → sleep 10s 继续
  自适应批量：落后 >= 500 块 → 一次 1000 块；否则直接追到链头
  eth_getLogs(start, end, address=OrderBook)
    └ 失败时：把范围缩到单块重试，仍失败 → sleep 10s 重试，断点不推进
  按 topic[0] 分发到 4 个 handler
  lastSyncBlock = endBlock + 1
  UPDATE ob_indexed_status
```

**必须回答的三个问题**：

1. **为什么等 8 个确认块？** 降低重组概率；代价是数据延迟。
2. **重组怎么发现？** 同一 `tx_hash` 出现在不同 `block_number`（`checkAndHandleFork:816`）→ 回滚订单状态 + 删除失效 activity → 重新处理。
3. **事件处理失败会重试吗？** 看代码：handler 内部出错只打日志并 `return`，**不会中断循环，断点仍会推进**。这意味着单条事件失败会导致永久丢数据。这是本项目真实的一致性缺口，也是很好的深挖题。

### 5.3 三层时效

| 数据 | 延迟 | 原因 |
|---|---|---|
| 订单/活动 | 8 确认块 + 10s 轮询 | 扫块机制 |
| 地板价 | 再叠加 2 跳 Redis 队列 | Sync → 队列 → OrderManager |
| 挂单数 | 最多 60s | 每分钟重算 |
| 合集详情地板价 | 即时 | 请求时现场 SQL 计算 + 顺带修复 |

这就是文档里说"挂单后要等 10~30 秒"的根本原因。

### 5.4 链上↔链下的三种交互方式

讲架构时按这个分类最清楚：

| 方向 | 方式 | 用途 | 例子 |
|---|---|---|---|
| 读链 | `eth_call` | 校验/补全数据 | Sync 拉 tokenURI、`ownerOf`、`CheckNFTApprovalStatus`；Backend 导入时 `FetchNftOwner` |
| 读链（事件） | `eth_getLogs` | 增量同步 | 4 类 topic |
| 写链 | 服务端私钥签名 | 代用户发交易 | MetaNode 铸造（`metanode.go:384` 解析私钥 → `bind.NewKeyedTransactorWithChainID`） |

注意：**普通交易不经后端**，用户钱包直接签名发送。后端只在"平台代付"场景持私钥。

## 6. 后端 API 设计要点

### 6.1 分层与约定

```
GET /api/v1/xxx?filters={"...JSON..."}
  → Handler 解析 filters
  → chainIDToChain 映射链名（硬编码 1/10/11155111）
  → Service 聚合
  → DAO 查询
  → xhttp.OkJson(c, {result: ..., count: ...})
```

**表名按链后缀区分**：`multi.OrderTableName(chain)` → `ob_order_sepolia`。这是"一个库支持多链"的最简单做法。

### 6.2 三个值得精读的接口

| 接口 | 位置 | 学什么 |
|---|---|---|
| `/portfolio/listings` | `service/v1/portfolio.go:371` | 多链分组 → 并发查询 → 合并最佳 Bid |
| `/collections/:address/items` | `dao/items.go:63` | 一条 SQL 用 JOIN + `min(price)` + `GROUP_CONCAT` 拼出列表页 |
| `/bid-orders` | `service/v1/order.go:14` | 单品 Bid 与合集 Bid 的优先级合并算法 |

第三个最考业务理解：**一个 NFT 的最佳出价，应该取单品 Bid 还是合集 Bid？** 代码做法是把合集 Bid 按价格排序，分配给"还没有单品 Bid"的 tokenId。

### 6.3 鉴权（必须知道的现状）

```
GET  /user/:address/login-message → 生成 nonce 存 Redis
POST /user/login {message, signature}
     ├ 校验 message 里的 nonce 与 Redis 一致
     ├ ⚠ 签名没有校验（service/v1/user.go:35 明确写着 todo）
     ├ token = AES-OFB("login:address:data:<addr>", 硬编码盐)  ← 对同一地址恒定
     └ Redis SETEX 30 天
后续请求：header session_id → 解密 → 查 Redis 是否存在
```

中间件行为：`session_id` 为空时**直接放行**（`middleware/auth.go:26`），需要身份的地方再显式调 `GetAuthUserAddress`。

讲解时诚实处理这段：说清"这是可选登录设计，签名校验是待补齐项"，比硬说"做了签名认证"更可信。

### 6.4 缓存

只挂在两个路由上（合集榜单、NFT 图片），TTL 60 秒，key = `path + query + body`，只缓存 HTTP 200。

**为什么不全站缓存**：订单秒级变化，详情页缓存 60 秒可接受，列表页会导致"刚买完还在售"。

## 9. 讲解稿模板

### 3 分钟版（讲业务和架构）

> 这是一个链上订单簿型 NFT 市场。核心业务是挂卖单、挂买单、撮合成交，支持单件和合集两种出价粒度。
> 架构分四层：合约层里 OrderBook 负责订单校验、订单簿存储和撮合，Vault 负责按订单托管 NFT 和 ETH，只有 OrderBook 能操作金库；索引层 EasySwapSync 轮询链上事件，把订单、NFT、成交记录投影到 MySQL，同时维护地板价、挂单数、过期状态这些派生指标；后端是只读查询 API；前端负责钱包交互。
> 最核心的设计是：**资产按订单维度托管，成交在链上原子完成，链下数据库只承担查询和统计，链上才是最终真相。**

### 10 分钟版（加实现细节）

在 3 分钟版基础上补三块：

1. **成交的两条路径**：卖家接受 Bid 时卖家付 Gas 且不传 ETH，成交价取 Bid 价；买家买挂单时成交价取卖单价，多付退回。协议费留在合约里由 owner 提取。
2. **数据一致性**：唯一键 + OnConflict 保证幂等；8 个确认块降低重组影响；发现同一 tx 换块就回滚派生数据重扫；断点每批持久化。
3. **派生数据管线**：地板价不是实时 SQL，而是事件驱动增量维护 Top-100 最小堆，只有变化才写库；另有 10 秒全量快照用于算涨跌幅；详情接口还会现场算一次并投递修复事件。

### 演示"我有自己的判断"

> 项目里有几处我认为可以改进：订单没有做签名校验，靠 `maker == msg.sender`，所以不支持链下签名订单；登录流程签名校验还没实现，token 对同一地址是恒定值；同步服务单条事件失败时只记日志、断点仍推进，存在丢事件窗口。这些问题我都想过改法——比如引入 EIP-712 验签 + nonce 防重放，同步侧改成"整批事务 + 失败不推进断点"。

## 10. 迁移到同类 Web3 项目的方法

学完这个项目，再看任何 Web3 后端，都可以用同一套七问：

| # | 问题 | 本项目答案 |
|---|---|---|
| 1 | 链上负责什么，链下负责什么？边界在哪？ | 链上资产与成交，链下查询与统计 |
| 2 | 数据怎么从链上到数据库？ | 轮询 `eth_getLogs` + 确认块 + 断点 |
| 3 | 幂等靠什么？ | 唯一键 + OnConflict |
| 4 | 重组怎么办？ | 检测 tx 换块 + 回滚派生数据 |
| 5 | 哪些是派生/聚合数据？怎么维护？ | 地板价、挂单数、排行、涨跌幅 |
| 6 | 后端能不能只读？不能的话写在哪？ | 几乎只读，写侧三处边界 |
| 7 | 一次用户操作的完整链路？ | 钱包签名 → 合约 → 事件 → 索引 → API → 页面 |

第 5 问最能体现水平：**大部分 Web3 项目 80% 的复杂度不在"读链写库"，而在这些派生指标怎么高效维护、怎么保证和链上一致。**

## 11. 已知设计缺陷（当作深挖题，不要当结论背）

这些是读代码得出的观察，适合作为"讲讲你认为还有什么可以改进"的素材：

| # | 观察 | 位置 |
|---|---|---|
| 1 | 订单无签名校验，只靠 `maker == msg.sender`，不支持链下签名订单 | `_makeOrderTry:526` |
| 2 | 登录流程未验签，token 对同一地址恒定，加密盐硬编码 | `service/v1/user.go:33-95` |
| 3 | 同步侧单事件失败只打日志，断点仍推进 → 可能丢事件 | `service.go:117-232` |
| 4 | 事件逐条写表，无显式事务包裹 | 各 handler |
| 5 | 展示用地板价 SQL 未过滤 `expire_time`，与历史快照口径不一致 | `dao/collection.go:338` |
| 6 | `sale_price` 字段名与注释不符（实际是 CollectionBid 最高价） | `dao/collection.go:408` |
| 7 | 链 ID → 链名映射硬编码三链，与配置 `chain_supported` 两套来源 | `api/v1/util.go:9` |
| 8 | `collection.go` 里的 `MintNFT` 是 mock（假 txHash），真实铸造在 `metanode.go` | 两者对比阅读 |
| 9 | 撮合后卖单只更新状态，不保证从队列移除 | `_matchOrder` 分支 2 |

第 9 条可以自己在测试里验证：`EasySwapContract/test/TestEasySwap.js` 有 46 个通过的用例，是最可靠的可执行规格。
