1. 产品总览：市场到底要完成什么

NFT 市场不是图片展示站，而是“资产发现 + 订单表达 + 撮合 + 原子结算 + 历史数据”的完整系统。

用户问题

  • 买家找不到可靠、可比较的 NFT 和价格。
  • 卖家无法公开表达卖价、接受报价或批量交易。
  • 双方不愿把资产先交给陌生人托管。
  • 链上原始事件难以直接用于搜索、排名和 Portfolio。

产品承诺

  • 所有权和成交结果由链上合约最终确认。
  • 订单有价格、数量、有效期和取消语义。
  • 成交时 NFT 与资金原子交换，要么全成要么全败。
  • 链下服务提供快查询、可读状态和运营能力。
推荐定位：首期做“单链 + ERC-721 + 原生 ETH/WETH + List/Bid/Collection Bid”的闭环。先把资产安全、订单状态和数据一致性做对，再扩展多链、ERC-1155、聚合市场和 AMM。

2. 业务建模：角色、资产和收益

2.1 角色

角色目标获得承担/失去
卖家 Seller出售自己持有的 NFT成交价、流动性、价格发现NFT、Gas、平台费、价格上涨后的潜在收益
买家 Buyer买入 NFT 或取得某种权益NFT 所有权、使用权、转售权ETH/WETH、Gas、价格下跌风险
创作者 Creator发行资产、经营品牌或内容发行收入、社区、授权和可能的版税运营、版权、合约和声誉风险
平台 Platform提供发现、订单、撮合、结算和数据服务协议费、数据和网络效应合约安全、基础设施、索引和客服成本
执行/索引服务监听事件、补扫、更新派生数据运营权限、服务收入（若独立）RPC、数据库、重组和数据错误风险

2.2 资产权益

NFT 本体

由 (chainId, collection, tokenId) 唯一确定。ERC-721 数量固定为 1；若支持 ERC-1155，还要增加数量与批量转移语义。

订单权利

订单不是 NFT 所有权，而是“在条件满足时，以约定价格交换资产”的可验证意愿。订单可以被取消、过期、部分成交或完全成交。

使用权益

会员、游戏道具、门票、品牌授权等由项目方业务定义。交易市场只能确认 token 归属，不能自动保证现实权益。

平台费用

建议明确协议费、创作者版税、买方/卖方承担方、最小费用、舍入方向和费率上限。费用规则必须在成交前展示。

2.3 收益公式

成交总价 = 单价 × 成交数量
协议费 = 成交总价 × 协议费率
创作者版税 = 成交总价 × 版税率（若启用且能执行）
卖家净收入 = 成交总价 - 协议费 - 创作者版税 - 其他费用
买家总成本 = 成交总价 + 买方承担费用 + Gas
业务边界：平台的收入不是成交额本身，而是成交额乘以明确的收费比例。成交额只是 GMV；平台还需要支付 RPC、数据库、前端、运营和安全成本。

3. 订单模型：订单簿如何表达买卖意愿

3.1 统一订单结构

Order {
  chainId: uint256,
  exchange: address,
  side: List | Bid,
  saleKind: Item | Collection,
  maker: address,
  asset: { collection, tokenId, amount },
  paymentToken: address,      // address(0)=ETH
  price: uint256,              // 单位价格
  quantity: uint256,
  startTime: uint64,
  endTime: uint64,             // 0 表示不过期
  salt: uint256,
  nonce: uint256,
  fees: Fee[],
  signature: bytes
}

3.2 四种核心订单

Item Listing

卖家指定 collection + tokenId + price。最容易理解，适合首期。

Item Bid

买家指定一个具体 tokenId，报价通常需要锁定 WETH/ETH 或在成交时支付。

Collection Bid

买家只指定 collection，卖家可以用集合中的任意符合条件的 token 接受。

Trait/Criteria Bid

买家指定属性条件。需要额外的链下属性索引和链上校验，建议后置。

3.3 订单簿排序

订单方向第一排序第二排序过滤条件
List价格从低到高创建时间从早到晚有效期、数量、资产仍可交付
Bid价格从高到低创建时间从早到晚余额/授权、有效期、报价仍可成交

数据结构可以使用“价格索引 + 同价 FIFO 队列”。链上需要强一致和可验证；链下可以使用 PostgreSQL 的索引表、Redis 缓存和按 collection 分片的撮合视图。

3.4 订单唯一性

推荐用 EIP-712 结构哈希作为 orderHash，并把 chainId、exchange、paymentToken、salt、nonce 纳入签名域，防止跨链重放、跨合约重放和旧订单重用。

4.1 状态转换

动作前置条件状态变化资产变化
创建 Listing持有 NFT 且授权→ OPENNFT 托管或保持在卖家钱包
创建 Bid余额足额或允许成交时支付→ OPENETH/WETH 托管或授权
撮合双方订单有效、资产匹配OPEN → FILLED / PARTIALNFT 与资金原子交换
取消maker 或授权执行者OPEN → CANCELLED退回剩余托管资产
过期当前时间 > endTimeOPEN → EXPIRED不能成交，资产按取消/退款规则处理
编辑允许修改的字段变化旧订单取消 + 新订单创建差额补缴或退款

4.2 用户看到的状态

前端不要只显示“成功/失败”，至少需要区分：等待钱包签名、交易已提交、等待确认、链上成功、链上回滚、订单已被抢先成交、订单已过期、索引服务尚未同步。

重要：时间到达不会自动触发链上交易。过期是合约在下一次查询/撮合时判断的逻辑状态；如果需要返还托管资产，仍需取消或清理交易。

5. 链上合约架构

OrderBook订单入口、撮合、取消、编辑、批量调用
OrderValidatorEIP-712/EIP-1271、过期、nonce、成交量校验
Vault / ConduitNFT、ETH/WETH 托管和授权转移
Fee / Royalty协议费、创作者版税、分润和提取

5.1 推荐合约模块

  1. Exchange：外部入口，处理 createOrder、cancel、fulfill、bulkFulfill。
  2. OrderValidator：验证签名、域、nonce、资产、价格、有效期和订单状态。
  3. Settlement：统一计算付款、费用、版税和退款，按固定顺序执行资产转移。
  4. Vault/Conduit：可选托管模型。更安全直观，但用户要先锁定资产；非托管模型体验更好，但成交时要重新验证余额和授权。
  5. NonceManager：支持单订单取消、批量 nonce 取消和全局 nonce 失效。
  6. ProtocolManager：管理费率、费收款地址、暂停和升级权限。

5.2 两种订单架构的取舍

方案特点优点缺点适用
托管型订单簿创建订单时 NFT/资金进入 Vault成交确定性高，订单簿清晰资金锁定、授权步骤多，合约风险集中EasySwap 当前形态、封闭生态
签名订单订单只在链下签名，成交时才转资产免锁仓、跨市场分发、体验好撮合时可能失效，需处理授权/余额竞争开放市场、聚合器、Seaport 类协议
混合型Bid 锁 WETH，List 用签名/授权转移兼顾确定性和低摩擦状态组合更复杂成熟产品的推荐方向

6.2 服务拆分

Market API

合集、NFT、订单、活动、排名、历史成交和 Portfolio 查询。只返回派生数据，不直接决定资产所有权。

Order Service

校验签名格式、接受订单、订单过期、报价聚合和可成交检查。撮合前必须再次链上模拟。

Indexer

按 block number + tx hash + log index 幂等消费。保存原始事件和派生状态，支持重组回滚。

Metadata Worker

读取 tokenURI、解析 JSON、提取图片和属性、缓存 IPFS/HTTP 结果，失败重试且保留旧值。

6.3 为什么不能只靠数据库撮合

数据库里的订单只是查询副本。用户可以在别的平台成交、撤销授权、转移 NFT 或消耗 WETH，因此每次成交都要以链上合约最终校验为准。链下撮合服务的职责是“找到候选订单和构造交易”，不是替代合约做资产裁决。

7.2 状态一致性规则

  • 订单主键是 chain_id + exchange + order_hash，不要只用 order_hash。
  • 事件唯一键是 chain_id + tx_hash + log_index。
  • 原始事件先落库，再异步更新 orders、tokens、collections 等派生表。
  • 链重组时按确认窗口回滚受影响区块，再重新扫描；不能直接删除一行数据了事。
  • 缓存必须带 block number 或 version，避免旧数据覆盖新数据。

9. 撮合与结算：一笔交易如何安全完成

9.1 买家吃卖单

查询最低有效 List
→
检查 expiry / filled / owner / approval
→
构造 taker order
→
eth_call 模拟
→
提交 fulfill
→
确认 NFT + 资金事件

9.2 卖家接受 Bid

卖家选择一个仍有效的 Bid，合约检查 collection、tokenId/criteria、价格、数量、买家资金和双方订单哈希，成功后将 NFT 给买家，将成交价扣除费用后给卖家。

9.3 原子结算顺序

  1. 验证订单域、签名、时间、nonce、数量和资产匹配。
  2. 验证订单未取消、未完全成交，且付款资产足够。
  3. 计算成交价、协议费、版税、卖家净额和退款。
  4. 更新订单成交量，防止重入和重复成交。
  5. 执行 NFT 转移和资金转移。
  6. 发出成交、费用和资产转移事件。
不要依赖前端计算：价格、费用、剩余数量、版税和退款都必须在合约重新计算。前端报价只用于展示，不能作为结算可信源。

9.4 批量交易

批量撮合需要明确两种语义：原子批量（任一失败全部回滚）和部分成功（返回每笔成功状态）。部分成功尤其要返回每个子调用的错误码、orderHash 和实际成交数量，否则用户会误以为全部成交。

10. 安全、一致性与运维

0重复成交
1原子结算
≥N确认区块
100%资产可追溯

10.1 合约安全

  • 使用重入保护、暂停开关、权限分离和升级多签。
  • 签名域绑定 chainId、exchange、版本和 nonce，防止重放。
  • 支持合约钱包的 EIP-1271 签名校验。
  • 对 ERC-721/1155 的接收、数量、safeTransfer 和回调做兼容测试。
  • 费用和提币权限单独审计，协议费率设置上限。
  • 升级前检查 storage layout；生产实现合约锁定，代理管理员使用多签。

10.2 链下安全

  • API 不能凭数据库状态声称“拥有 NFT”；owner 以链上查询或已确认索引为准。
  • 所有写接口使用 nonce 登录、签名验证、限流、审计日志。
  • RPC 不稳定时自动切换、重试和告警，避免重复提交相同交易。
  • 元数据 URL、图片上传和回调防 SSRF、恶意 SVG、越权覆盖和超大文件。
  • 索引器保存 checkpoint、原始日志、重试次数和 dead-letter 任务。

10.3 可观测性

指标告警条件
Indexer lag最新链头与已处理区块差距超过阈值
Order mismatch数据库订单状态与链上 filled/cancel 状态不一致
Settlement revert撮合回滚率异常升高、授权或余额错误集中出现
Vault balance托管资产与订单剩余数量无法对账
API latency订单、合集或 Portfolio P95 超过目标

11. 推荐落地路线

MVP：单链、ERC-721、ETH/WETH、List + Item Bid
  • Exchange、Vault、EIP-712、创建/取消/成交。
  • Indexer、合集/NFT/订单/成交表。
  • 市场页、详情页、Portfolio、钱包交易状态。
  • 安全测试、事件幂等、基础监控和测试网验收。
阶段 2：Collection Bid、批量交易、编辑和更好流动性
  • 集合出价、批量撮合、订单聚合、报价比较。
  • 允许部分成功并逐笔展示结果。
  • WETH 授权、gas 估算、交易模拟和失败恢复。
阶段 3：多链、ERC-1155、第三方聚合
  • 按 chainId 隔离配置、合约、索引 checkpoint 和费用。
  • 增加数量型资产、批量转移和部分成交。
  • 接入外部订单源，建立统一订单适配层。
阶段 4：高级业务
  • Trait Bid、租赁、NFT 抵押、游戏资产、品牌会员。
  • AMM 或流动性池；必须与订单簿模型分开设计。
  • 数据 API、项目方后台、发行和营销工具。

最终建议

如果要把 EasySwap 做成真正可用的交易市场，优先级不是继续堆页面，而是先把三条链路做成闭环：订单正确性、资产原子结算、链上链下可恢复一致性。

  1. 先确定订单模型和费用/版税规则，写成不可歧义的状态机。
  2. 再确定托管型、签名型或混合型订单架构，不要中途改变资产语义。
  3. 所有合约事件和数据库状态都设计成可重放、可对账。
  4. 最后再扩展多链、聚合、AMM 和复杂金融化功能。
