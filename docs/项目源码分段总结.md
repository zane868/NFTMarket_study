# NFTMarket 项目源码分段总结

整理日期：2026-11-17。

本总结仅以项目中的 Solidity、Go、TypeScript、TSX 和 JavaScript 源码及测试代码为依据，没有读取现有 Markdown、设计文档、配置文件内容、依赖清单或部署产物。重点阅读了核心业务实现和模块间调用关系，公共工具与重复 UI 组件按职责归纳。下文所述是当前源码的静态行为，本次没有运行服务、测试或链上交易，也没有验证实际部署状态。

## 第一段：项目整体在做什么

项目实现了一个以 ERC721 NFT 和原生 ETH 为主要交易资产的市场。用户可以浏览合集、查看单个 NFT、挂卖单、挂单品或合集买单、购买 NFT、接受出价、撤单、改价，以及上传素材并铸造 MetaNodeNFT。

整体采用“链上交易与托管，链下索引与查询”的结构。交易由钱包直接调用订单簿合约；合约把资产交给 Vault 托管，并通过事件公布订单变化；同步服务将事件转换成数据库记录；后端组合数据库、Redis 和 RPC 数据供前端展示。因此，链上交易确认与页面数据更新是两个阶段。

| 目录 | 代码职责 | 核心入口 |
| --- | --- | --- |
| `EasySwapContract` | 订单簿、订单校验、资产托管、费用和 NFT 合约 | `contracts/EasySwapOrderBook.sol` |
| `EasySwapSync` | 轮询链上日志，维护订单、NFT、活动及统计数据 | `cmd/daemon.go`、`service/orderbookindexer/service.go` |

## 第二段：订单模型与订单标识

`LibOrder` 定义了整个交易系统的基础数据结构。`Side` 的值是 `List = 0`、`Bid = 1`；`SaleKind` 的值是 `FixedPriceForCollection = 0`、`FixedPriceForItem = 1`。这两组数值也被前端合约服务和同步服务使用，跨端编码必须保持一致。

一笔 `Order` 包含方向、销售类型、创建者、NFT 资产、单价、到期时间和盐值。NFT 资产又由 `tokenId`、`collection`、`amount` 组成。价格使用 `uint128`，数量使用 `uint96`，到期时间和盐值使用 `uint64`。卖单创建时数量必须为 1，买单可以锁定多份购买额度。

订单的唯一标识 `OrderKey` 是 `bytes32`。`LibOrder.hash(Asset)` 使用 `abi.encode`；`LibOrder.hash(Order)` 将类型哈希、字段和资产哈希通过 `abi.encodePacked` 打包后再取 Keccak256。零值 `OrderKey` 被用作链表结束、空结果等场景的哨兵。

前端 `computeOrderKey()` 使用相同的字段类型和打包方式复现订单哈希。虽然合约继承并初始化了 EIP712 模块，但当前交易入口没有传入或验证离线订单签名的流程，不能仅凭 EIP712 的继承关系认定已经实现离线签名订单。

源码入口：[LibOrder](../EasySwapContract/contracts/libraries/LibOrder.sol)、[OrderValidator](../EasySwapContract/contracts/OrderValidator.sol)、[前端订单哈希](../nft-market-fe/contracts/service/orderBookContract.ts)。

## 第三段：链上订单簿的数据结构

`OrderStorage` 将存储拆成三层：`orders[orderKey]` 保存订单与下一节点；`priceTrees[collection][side]` 保存价格红黑树；`orderQueues[collection][side][price]` 保存同价订单队列的头尾节点。

红黑树只管理价格档位，卖单从最低价开始，买单从最高价开始。同一个价格档位里的订单通过单向链表连接，新订单放在队尾，因此查询具备价格优先、同价按插入顺序遍历的结构。这里的时间顺序来自插入顺序，并没有额外的链上创建时间字段参与排序。

新增订单时，先检查哈希是否重复，再按需插入价格节点，最后将订单追加到队尾。删除订单时，需要从对应价格档的链表头查找前驱节点，摘除订单后，如果队列为空，再删除红黑树中的价格节点。

价格树操作按红黑树结构具有对数级复杂度；删除某个订单仍需线性扫描同价链表。`getOrders()` 和 `getBestOrder()` 负责遍历及筛选，它们本身不会检查 `filledAmount`，也不会自动清除所有已成交节点。因此，“查询返回订单”和“订单仍能撮合”需要分开判断。

另外，`getOrders()` 返回长度为 `count` 的定长数组，实际记录不足时尾部保留零值。前端读取时需要过滤这些空订单。

源码入口：[OrderStorage](../EasySwapContract/contracts/OrderStorage.sol)、[RedBlackTreeLibrary](../EasySwapContract/contracts/libraries/RedBlackTreeLibrary.sol)。

## 第四段：订单簿与 Vault 如何分工

`EasySwapOrderBook` 负责交易规则、订单状态和撮合；`EasySwapVault` 负责保管 NFT 与 ETH。Vault 的主要资产操作受 `onlyEasySwapOrderBook` 限制，订单簿地址由 Vault 的 Owner 设置。

挂卖单时，NFT 从卖家转入 Vault；挂买单时，`单价 × 数量` 的 ETH 转入 Vault。Vault 使用 `ETHBalance[orderKey]` 和 `NFTBalance[orderKey]` 按订单记账，其中 `NFTBalance` 存储的是 tokenId，而不是 NFT 数量。合集地址等信息由订单簿在后续调用时提供。

改单时，卖单通过 `editNFT()` 迁移订单与 NFT 的关联；买单通过 `editETH()` 按新旧额度差额补款或退款。成交和撤单时，由订单簿指示 Vault 释放资产。Vault 还实现 ERC721 接收回调，以及用户主动调用的批量 NFT 转账入口。

前端授权的对象是 Vault。`approveNFT()` 同时支持单个 token 的 `approve` 和整个合集的 `setApprovalForAll`，`checkNFTApproval()` 会检查这两种授权状态。

源码入口：[EasySwapVault](../EasySwapContract/contracts/EasySwapVault.sol)、[前端授权与合约调用](../nft-market-fe/contracts/service/orderBookContract.ts)。

## 第五段：创建、取消与编辑订单

`makeOrders()` 遍历订单数组。创建时检查 maker 是否为调用者、价格和盐值是否非零、有效期是否合法，以及订单哈希是否已经被成交或取消。卖单数量必须为 1，买单数量必须大于 0；随后执行托管、写入订单簿并发出 `LogMake`。成功买单所需的 ETH 被累计，多余的传入 ETH 会退回。

`cancelOrders()` 根据订单 key 读取订单，只允许 maker 取消未完全成交的订单。卖单归还 NFT；买单按未成交数量返还 ETH。取消后，订单从存储链表移除，`filledAmount` 设为 `uint256` 最大值，防止同一个订单哈希继续使用。

`editOrders()` 的实质是删除旧订单、标记旧哈希取消、创建新订单，再迁移 Vault 中的资产关联。方向、销售类型、maker、合集和 tokenId 必须保持一致；价格、数量、有效期和盐值可以通过新订单改变。买单按旧单剩余锁定金额与新单总金额计算补款或退款。

需要注意，编辑路径没有完整复用创建路径的所有校验，例如没有同样显式检查卖单数量必须为 1。描述或扩展这部分功能时，应以两个函数各自的检查条件为准。

源码入口：[EasySwapOrderBook：makeOrders、cancelOrders、editOrders 及内部实现](../EasySwapContract/contracts/EasySwapOrderBook.sol)、[成交量与取消标记](../EasySwapContract/contracts/OrderValidator.sol)。

## 第六段：撮合与资金结算

`matchOrder()` 接收一张卖单和一张买单，由 `_matchOrder()` 根据调用者身份进入两个分支。撮合是用户显式提交订单对触发的；价格树提供查询能力，当前代码没有后台自动交叉撮合引擎。

卖家接受买单时，调用者必须是卖单 maker，且不能额外传入 ETH。买单必须已经在订单簿中；卖单可以已入簿，也可以临时构造。成交价取买单单价，资金从买单的 Vault 余额中扣除，NFT 从 Vault 或卖家钱包交付给买家。

买家购买卖单时，卖单必须已经在订单簿中，成交价取卖单单价。买单可以已经入簿，也可以临时构造；临时买单通过本次交易的 `msg.value` 付款。前端 `buyNow()` 使用的就是临时买单路径，并将买单价与卖单价设为相同值。

两种路径都计算协议手续费，再把剩余 ETH 发给卖家。费用留在订单簿合约中，Owner 可调用 `withdrawETH()` 提取。`LibPayInfo` 定义分母为 10000、费用上限为 1000，因此上限是 10%；部署脚本传入 200，对应 2%，这只是脚本参数，不代表已部署合约的实时费率。

撮合前还会检查买卖方向、卖单类型、maker 不同、订单未关闭，以及资产匹配条件。当前合集买单的匹配条件存在合集地址校验缺口，详见第十六段。

源码入口：[撮合与费用结算](../EasySwapContract/contracts/EasySwapOrderBook.sol)、[费用常量](../EasySwapContract/contracts/libraries/LibPayInfo.sol)、[前端 buyNow](../nft-market-fe/contracts/service/orderBookContract.ts)、[部署脚本](../EasySwapContract/scripts/deploy.js)。

## 第七段：批量操作与 multicall 的真实语义

`makeOrders()`、`cancelOrders()`、`editOrders()` 虽然返回每项结果，但并没有为每项操作都建立独立的异常捕获边界。部分参数不合法时可以跳过，资产转移等内部调用一旦 revert，仍可能使整笔交易回滚。

`matchOrders()` 则为每一组订单使用 `delegatecall` 调用 `matchOrderWithoutPayback()`。子调用失败时记录 `BatchMatchInnerError` 并继续处理后面的订单；成功结果和已消费金额会累计，最后统一退回多余 ETH。因此，它允许逐项失败，与函数注释中“全部成功或全部失败”的描述不一致。外层后续操作如果失败，整笔交易仍会回滚。

`multicall()` 可以在一笔交易中串联创建、取消、编辑和撮合操作。它限制可调用的 selector，并要求最多包含一个可能消费 `msg.value` 的子调用，以减少 delegatecall 下各子调用重复看到同一金额带来的歧义。

`revertOnFail = true` 时，失败会使整个 multicall 回滚；为 `false` 时，记录 `MulticallInnerError` 后继续。该选项控制的是子调用 revert；子调用内部返回“跳过某订单”等业务结果时，还需要继续检查相应返回值或事件。

源码入口：[matchOrders 与 multicall](../EasySwapContract/contracts/EasySwapOrderBook.sol)、[multicall 测试](../EasySwapContract/test/TestEasySwap.js)。

## 第八段：合约权限与升级结构

订单簿使用初始化函数组合 Ownable、ReentrancyGuard、Pausable、OrderStorage、ProtocolManager 和 OrderValidator。交易主入口包含暂停检查，创建、取消、编辑和撮合主入口包含重入保护。Owner 可调整协议费率、更换 Vault、暂停或恢复交易，以及提取订单簿中的 ETH。

Vault 同样采用初始化和 Owner 管理。部署脚本使用 `upgrades.deployProxy()` 部署 Vault 与 OrderBook，并在部署后调用 `Vault.setOrderBook()` 连接两者。合约中保留了多个 `__gap`，供未来存储扩展使用。

`MetaNodeNFT` 的结构不同：它使用构造函数初始化 ERC721 和 Owner，继承 `ERC721URIStorage`，tokenId 从 1 自增，`safeMint()` 仅限 Owner 调用，并为每个 token 写入 URI。当前源码没有市场自动版税分配逻辑；`LibPayInfo` 的存在也不等于已经实现创作者版税结算。

源码入口：[订单簿](../EasySwapContract/contracts/EasySwapOrderBook.sol)、[Vault](../EasySwapContract/contracts/EasySwapVault.sol)、[MetaNodeNFT](../EasySwapContract/contracts/MetaNodeNFT.sol)、[部署脚本](../EasySwapContract/scripts/deploy.js)。

## 第九段：同步服务如何启动和追块

`EasySwapSync` 通过 Cobra 的 `daemon` 命令启动，创建 MySQL、Redis、链客户端、合集过滤器、订单索引器和 OrderManager。启动时先预加载合集，再启动索引和订单管理后台任务。服务工厂为 Ethereum、Optimism、Sepolia 构造订单簿同步器；这不代表其他目录中出现的所有链都已经接通同样的同步流程。

`SyncOrderBookEventLoop()` 从数据库读取 `chain_id + index_type` 对应的同步游标，轮询最新区块高度。代码对已列出的链预留 8 个区块的确认距离，再从游标开始调用 `FilterLogs()`。

追块参数 `SyncBlockPeriod = 1000`，由于查询区间包含首尾，`endBlock = startBlock + SyncBlockPeriod` 最多覆盖 1001 个区块。接近链头时允许小范围同步，查询范围过大导致 RPC 错误时退回单区块重试。`SleepInterval` 为 10 秒，用于相应错误或等待分支。

日志按 topic 分发给创建、取消、撮合和 Approval 处理函数。处理完区间后，将游标更新为 `endBlock + 1`。当前过滤地址只包含订单簿合约，因此源码中虽然实现了 ERC721 Approval 处理，常规 NFT 合约发出的 Approval 日志不会仅靠这一过滤条件自动进入该分支。

源码入口：[daemon 启动](../EasySwapSync/cmd/daemon.go)、[服务装配](../EasySwapSync/service/service.go)、[索引循环](../EasySwapSync/service/orderbookindexer/service.go)。

## 第十段：链上事件如何变成业务数据

`handleMakeEvent()` 解码 `LogMake`，根据方向和销售类型将订单分类为卖单、合集买单或单品买单，写入订单记录，并尝试建立 NFT 与元数据记录。卖单还会更新 item 的 owner、价格、在售字段，以及合集名称、符号、图片和地板价。最后记录活动并把订单推送给 OrderManager。

`handleMatchEvent()` 根据事件中 `MakeOrder.Side` 判断哪个结构是买单、哪个是卖单，更新卖单状态和买单剩余数量，然后写入成交活动、更新 NFT owner、清理上架信息并发布价格更新事件。注意，事件中的 make/take 不是永远固定代表卖/买，两个撮合分支的参数顺序不同。

`handleCancelEvent()` 将订单置为取消，记录相应取消活动并推送价格更新事件；只有取消卖单时才清理 item 的上架字段。编辑订单发出的是旧单 `LogCancel` 加新单 `LogMake`，因此链下通过这两个已有事件感知改价。

同步器有补建合集、读取链上 `name`、`symbol`、tokenURI、检测接口及回填图片等逻辑，也有每日地板价快照及历史清理流程。部分创建操作使用 `OnConflict DoNothing`，但这只能提供局部重复写入处理，不能据此认定整个事件处理具有事务性或完整幂等性。

还有一个展示语义值得注意：卖单托管后，数据库 item.owner 仍记录卖家，而链上 ERC721 的 owner 已是 Vault。这使后端可以按卖家的业务持仓组织挂单，但数据库 owner 不能在所有场景下直接当作链上 `ownerOf()` 的返回值。

源码入口：[事件处理与元数据补全](../EasySwapSync/service/orderbookindexer/service.go)、[Order 模型](../EasySwapBase/stores/gdb/orderbookmodel/multi/order.go)、[Activity 模型](../EasySwapBase/stores/gdb/orderbookmodel/multi/activity.go)。

## 第十一段：OrderManager 与链下衍生状态

`EasySwapBase/ordermanager` 负责接收订单通知、处理过期、维护地板价和上架数量。它启动四个后台任务：新订单监听、订单过期处理、地板价处理和合集上架数处理。Redis List 被用作订单通知和价格事件队列。

过期处理使用 3600 个槽位的时间轮，每秒推进一次，用圈数记录较远的任务。启动时从数据库恢复活跃订单；到期后更新链下订单状态并发布价格更新事件。这个流程没有发送撤单交易，因此订单过期不会自动从 Vault 取回资产，用户仍需要链上撤单释放托管。

地板价维护使用 `PriorityQueueMap` 保存价格候选，按上架、购买、取消、过期和转移等事件调整，再更新合集价格。这个名为优先队列的结构实际使用切片排序和 map，新增调用 `sort.Sort()`，删除通过遍历切片完成，并非堆实现。

上架数统计启动时全量计算，随后聚合发生变化的合集地址，每分钟重新统计并缓存。统计条件涉及卖单状态、maker 与业务 owner 的一致性等，属于链下派生指标。

源码入口：[OrderManager](../EasySwapBase/ordermanager/service.go)、[时间轮](../EasySwapBase/ordermanager/expiredorder.go)、[价格候选结构](../EasySwapBase/ordermanager/queue.go)、[地板价](../EasySwapBase/ordermanager/floorprice.go)、[上架数](../EasySwapBase/ordermanager/listcount.go)。

## 第十二段：Go 后端的分层与数据组织

后端从 `main.go` 创建 `ServerCtx`，初始化日志、MySQL、Redis、DAO 和按 chainId 管理的 NFT 链服务，再通过 Gin 注册路由并启动。调用结构主要是 `router -> api/v1 Handler -> service/v1 -> dao / NodeSrvs`，请求和响应结构集中在 `types/v1`。

Handler 负责解析和检查参数；Service 负责组合合集、NFT、图片、挂单、出价、历史成交等数据；DAO 负责 GORM 与 SQL 查询。`GetItem()` 会并发查询多个数据来源，并在单品买单与合集买单之间选择展示的较高出价。

公共模型按用途分布在 `base` 与 `multi`。订单、活动、NFT、合集等表名通过链名生成，例如 `ob_order_<chain>`、`ob_activity_<chain>`。价格采用 `decimal.Decimal` 或大整数，前端在展示时再进行 wei 与 ETH 的换算。

源码中可见的主要接口如下，均以 `/api/v1` 为前缀：

| 路径范围 | 职责 |
| --- | --- |
| `/user` | 登录消息、登录、签名状态 |
| `/collections` | 排行、合集详情、NFT 列表与详情、出价、特征、历史价格 |
| `/activities` | 多链活动查询 |
| `/portfolio` | 用户合集、持仓、挂单、买单和单个 NFT 导入 |
| `/bid-orders` | 按 NFT 查找可用出价组合 |
| `/upload` | 代理上传、COS 凭证与策略相关接口 |
| `/metanode` | MetaNodeNFT 铸造及链上查询 |
| `/admin` | 合约记录管理、同步任务与统计接口 |

合集排行会组合 Redis 中的成交缓存、数据库合集数据、价格变化和上架数。当前 `GetTopRanking()` 没有再按成交量对最终结果显式排序，因此不能只根据函数名推断最终结果总是按交易量排名。

## 第十三段：NFT 导入、素材上传与铸造

单个 NFT 导入已经包含实际链上读取：`ImportPortfolioItem()` 使用 `ownerOf()` 检查请求中的用户地址是否为 owner，再读取元数据并写入合集、NFT 和图片记录。没有元数据时使用默认名称；图片 URI 还会做长度和 data URI 过滤。这里验证的是请求地址与链上 owner 一致，并不自动证明 HTTP 请求者持有该地址的私钥。

铸造页面使用 `cos-upload-post.ts`，将图片和 metadata JSON 通过 `/upload/file` 发给后端，再由后端通过 COS SDK 上传。随后前端调用 `/metanode/mint`，传入接收地址与 metadata URI。

`MintMetaNodeNFT()` 是实际的链上调用实现：连接 RPC、读取 nonce、设置 Gas、用服务端 Owner 私钥创建交易签名器，调用 `safeMint()`，再等待交易回执并从 mint 的 `Transfer` 事件提取 tokenId。成功确认后尝试写入 NFT 和图片记录；等待 30 秒仍未取得回执时返回 pending。批量铸造逐笔调用该函数，最多接受 50 项，不是单笔链上批量交易。

另一路 `/collections/:address/mint` 对应的 `performMint()` 仍返回固定模拟交易哈希和 tokenId，不能与 MetaNode 的实际铸造实现混淆。管理员合约 CRUD 有 DAO 调用，但同步整个合集、同步指定 token、同步进度/历史和批量刷新元数据等功能仍包含 sleep 或固定数据占位。

源码入口：[持仓导入](../EasySwapBackend/src/service/v1/portfolio_import.go)、[上传服务](../EasySwapBackend/src/service/v1/cos.go)、[MetaNode 铸造](../EasySwapBackend/src/service/v1/metanode.go)、[通用铸造占位](../EasySwapBackend/src/service/v1/collection.go)、[管理功能](../EasySwapBackend/src/service/v1/admin.go)、[铸造页面](../nft-market-fe/app/mint/page.tsx)。

## 第十五段：三条主要业务链路

### 1. 卖家上架 NFT

用户进入持仓页，必要时先通过导入接口补齐 NFT；上架组件构造 `List + FixedPriceForItem` 订单，检查并授权 Vault，再调用 `makeOrders()`。合约将 NFT 转入 Vault，记录订单并发出 `LogMake`。同步器读取事件后写入订单、NFT 和活动数据，后端查询这些记录，页面再次请求后展示新的挂单。

### 2. 买家立即购买

单品页调用 `buyNow()`，从链上取候选卖单，检查是否已成交、过期或属于自己，再构造临时买单，按卖单价发送 ETH 并调用 `matchOrder()`。合约交割 NFT、向卖家付款并保留协议费。后续索引器应根据 `LogMatch` 更新展示数据，但当前临时买单路径存在提前返回问题，见下一段。

### 3. 上传并铸造 NFT

前端验证钱包连接、Sepolia 网络、图片和文本信息，将图片及 metadata JSON 上传至后端，再请求 `/metanode/mint`。后端使用合约 Owner 的签名调用 `MetaNodeNFT.safeMint()`，确认后提取 tokenId 并尝试入库。用户在这条流程中提供接收地址，链上铸造交易由服务端发送并支付 Gas。

这些链路表明：交易钱包、托管金库、服务端签名账户、索引服务和数据库各自承担不同职责。定位页面状态问题时，需要沿交易回执、合约状态、日志处理、数据库记录和 API 响应逐层核对。

## 第十六段：当前实现中需要明确的边界与问题

以下内容根据具体函数分支归纳，没有在本次工作中修改或运行复现。

### 1. 合集买单缺少同合集约束

`_isMatchAvailable()` 将“买单类型为合集买单”直接作为资产匹配条件的一种满足方式，没有在该分支同时要求买卖两侧的 collection 相同。按当前条件，合集买单没有被严格限制为只能接收其指定合集的 NFT。

### 2. 买家成交后，卖单存储可能残留

买家发起的 `_matchOrder()` 分支更新卖单 `filledAmount` 并释放 NFT，但没有对应调用 `_removeOrder(sellOrder)`。`getOrders()` 与 `getBestOrder()` 又不检查成交量，因此查询可能继续遇到已成交卖单。前端通过额外读取 `filledAmount` 缓解了候选有效性问题。

### 3. 单品购买候选未核对目标 tokenId

`OrderStorage.getOrders()` 的 tokenId 筛选只写在买单分支。前端 `findMatchableListing()` 虽然传入目标 tokenId，但遍历卖单候选时没有再检查候选的 tokenId 是否等于用户选择值。随后 `buyNow()` 用候选订单的 NFT 构造买单，因此目标合集存在多个 token 的挂单时，存在选中其他 token 的路径；而且它只取一批候选，没有继续翻页。

### 4. 立即购买事件可能无法完成入库更新

前端立即购买使用未入簿的临时买单；合约在买家分支将它作为 `LogMatch` 的 MakeOrder。索引器对应分支更新卖单后，继续强制查询这个买单的数据库记录，查不到就 return，导致后续成交活动、NFT owner 和下架信息更新无法完成。

### 5. 同步失败没有统一阻止游标前进

事件处理函数返回值为 void，部分解码、数据库或 RPC 错误仅记录日志并 return；外层仍可能把游标推进到区间结束之后。多张业务表之间也没有统一数据库事务，因此可能出现部分记录成功、部分记录缺失，并且没有由当前循环自动重试该事件的情况。

### 6. 分叉处理属于有限补偿

`checkAndHandleFork()` 通过“相同交易哈希、不同区块高度”的活动记录识别部分变化，再恢复部分订单状态和删除旧活动。它没有按区块哈希维护完整的规范链历史，也没有统一回滚所有衍生字段，不能覆盖所有重组和交易消失场景。

### 7. 永不过期订单的链上与链下含义不同

合约允许 `expiry = 0` 表示永不过期；OrderManager 多处直接将过期时间与当前时间比较，会把 0 当作已过期。部分 DAO 查询又仅接受 `expire_time > now`，也会排除这类订单。链上仍有效的订单因此可能在链下被标记或查询为失效。

### 8. 登录验证与认证中间件尚不完整

`UserLogin()` 的签名验证仍处于 TODO/注释状态，实际主要核对 nonce。`AuthMiddleWare()` 在缺少 `session_id` 时直接放行；管理员路由的专门角色中间件也未启用。部分 Handler 另有取用户地址的检查，但不能把整个注册了该中间件的路由组统一视为已严格认证。

此外，AES 登录代码使用的固定盐字符串不满足 AES 要求的密钥长度，同时忽略 `aes.NewCipher()` 返回的错误，登录加解密路径存在运行时失败风险。前端将 token 保存到 localStorage，但统一请求拦截器没有自动设置后端读取的 `session_id`。

### 9. COS 凭证接口返回配置中的长期密钥

`generateTemporaryCredentials()` 当前直接将配置中的 SecretID、SecretKey 放入响应，并将 SessionToken 留空，没有调用 STS 获取受限临时凭证；对应 `/upload/cos-token` 路由没有认证中间件。主铸造页面虽然走代理上传，但这个凭证接口本身仍被注册。

### 10. 服务端铸造 API 的权限范围较宽

合约的 `safeMint()` 有 onlyOwner 限制，但后端 MetaNode mint 和 batch-mint 路由没有认证中间件，实际由服务器持有的 Owner 签名执行。前端要求连接钱包和切换网络，不能等同于后端已经验证请求者权限。

### 11. 金额、数量及状态仍有跨端边界

前端合集出价弹窗使用浮点乘法并保留六位小数计算总 ETH，再转为 wei，可能与精确的链上 `单价 × 数量` 不一致。持仓页通过 `NFTBalance > 0` 判断托管状态，无法正确表达 tokenId 为 0 的 ERC721；部分大整数还被转成 JavaScript number，超出安全整数范围时有精度问题。

铸造页面对 pending 结果设置了延时展示成功的路径，且会把部分通用成功消息作为成功依据，没有在这些分支继续轮询链上确认。订单创建、撤销和编辑的提示也需要区分“交易确认”与“目标业务操作成功”，因为合约存在跳过单项的返回或事件。

### 12. 部分页面和能力仍是展示或占位

合集内 `RecentActivity` 组件使用本地固定数组；空投页以展示组件为主。管理员同步任务和通用 mint 接口仍有模拟实现。前端订单簿和 Vault 地址、链头 WebSocket 地址主要按 Sepolia 写定，而 Go 层存在多链结构，不能据此认定完整交易体验已经覆盖全部链。

上述问题的源码入口：[合约匹配](../EasySwapContract/contracts/EasySwapOrderBook.sol)、[订单查询](../EasySwapContract/contracts/OrderStorage.sol)、[前端候选与购买](../nft-market-fe/contracts/service/orderBookContract.ts)、[同步处理](../EasySwapSync/service/orderbookindexer/service.go)、[过期管理](../EasySwapBase/ordermanager/expiredorder.go)、[认证中间件](../EasySwapBackend/src/api/middleware/auth.go)、[登录服务](../EasySwapBackend/src/service/v1/user.go)、[COS 服务](../EasySwapBackend/src/service/v1/cos.go)、[路由](../EasySwapBackend/src/api/router/v1.go)。
